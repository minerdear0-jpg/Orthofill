# Orthofill 0.1 beta — описание

Дата: 2026-10-21. Статус: черновик на утверждение.

## Зачем

Ортодонт на приёме записывает активацию брекет-системы коротко и как попало:
«лигатурная, рабочий, класс по молярам 1, замена дуги верх 18 25 нити, низ 14 нити,
перепел, явка 4 нед». Из такой записи нужно получить полный протокол приёма по
классификатору клиники и вставить его в служебное медицинское ПО.

Orthofill превращает короткую запись в готовый текст протокола и кладёт его в
буфер обмена. Врач проверяет текст, при необходимости правит его в программе,
копирует и вставляет в служебное ПО.

Сейчас есть рабочий прототип: `ortodont_v4.py` (разбор записи + простой tkinter-GUI)
и `test_ortodont.py` (35 тестов разбора дуг + сверка с эталоном). Версия 0.1 beta —
это приведение прототипа к виду, пригодному для ежедневной работы врача на
Windows 11, в портативной сборке.

Успех: врач на приёме тратит на протокол секунды — набрал, Ctrl+Enter, вставил;
правит файл классификатора сам, без программиста; ошибки программы видны сразу,
а не обнаруживаются потом в медкарте.

## Пользователь и окружение

- Пользователь — врач-ортодонт. Не программист. Работает с Excel.
- Windows 11. Рядом открыто служебное ПО; окно Orthofill бывает и широким, и
  узкой колонкой сбоку.
- Данные обезличены: ФИО и иных идентификаторов пациента в записи нет (подтверждено
  заказчиком). Всё хранится только локально.

## Цели 0.1 beta

1. Нормальный интерфейс медицинского ПО (см. «Интерфейс»), версия «0.1 beta» видна
   в заголовке окна и в окне «О программе».
2. Файл классификатора — xlsx с любым именем и оговорённой структурой; врач сам
   добавляет/удаляет пункты, и программа работает с изменённым файлом без правки кода.
3. Тот же файл хранит эталоны «запись → идеальный протокол»; программа сверяет
   себя с ними при каждом открытии файла.
4. Ctrl+Enter: сформировать протокол и сразу скопировать в буфер.
5. Врач правит протокол в программе; может сохранить исправленный вариант как
   новый эталон в xlsx.
6. Журнал вводов и результатов в локальной SQLite-базе.
7. Портативная версия (папка с exe в zip) + exe одним файлом, собираемые на Windows
   одним скриптом PowerShell.

## Не входит в 0.1 beta

- Словарь сокращений врача («пп» → перепел) — следующая версия; журнал копит для
  него материал.
- Подсказки/автодополнение при вводе.
- Тёмная тема, установщик, автообновление, подпись exe.
- Сетевая работа, несколько пользователей, синхронизация.
- Обучаемые модели / LLM. Разбор остаётся правилами.

## Анти-цели (провал, даже если «работает»)

- Протокол молча неверен: программа что-то не распознала и ничего не сказала.
  Любое нераспознанное упоминание — видимое предупреждение.
- Программа пишет в xlsx врача без его явного действия, или портит файл при записи.
- Правка классификатора врачом (новый пункт, перенумерация) тихо ломает разбор.
- Медленный старт или лишние клики на приёме.

## Файл классификатора (xlsx)

Источник правды для классификатора и эталонов — xlsx врача. Имя файла любое.
Программа запоминает последний открытый файл и открывает его при запуске.

Структура (как в нынешнем `order.xlsx`), первый лист:

- Строка заголовка — та, где в колонке A стоит `ID_CLASS`. Строки выше игнорируются.
- **A `ID_CLASS`, B `CLASS_LIST`** — классификатор. Коды:
  - `1` … `5` — раздел (`Жалобы: активация`, `Лечение:` …);
  - `2b`, `4f` — пункт раздела; может быть одиночным (`4a осмотр.`) или группой
    с вариантами;
  - `2b1`, `4f3` — вариант группы. Вариант без родительской группы («сирота»,
    сейчас `4h1`/`4h2`) — условный самостоятельный пункт.
  - В тексте бывает `<br>`; переводы строк и лишние пробелы нормализуются.
- **C `ID_INPUT_RAW`, D `INPUT_RAW`, E `ID_CLASS_RESULT`, F `RESULT`** — эталоны.
  Эталон начинается со строки, где заполнена C (номер) и D (запись врача); строки
  ниже с заполненными E/F — идеальный протокол по строкам, до следующей строки с C.
  Колонки C–F независимы от A–B (живут на тех же строках листа).

Проверка файла при открытии (ошибки — блокируют работу с понятным текстом;
предупреждения — показываются, работать можно): нет заголовка, дубли кодов,
невалидный код, пункт без текста; эталон, не совпадающий с результатом программы
(с указанием, какие строки разошлись).

## Как собирается протокол

Текст протокола в буфере — строки колонки F эталона, через перевод строки, без кодов.
Значит, программа формирует ровно такие строки, как в F: и набор кодов, и текст.
Сверка с эталонами сравнивает и коды, и текст (после нормализации пробелов).

Правила (переносятся из `ortodont_v4.py`, ключевое изменение — привязка к тексту):

1. **Правила привязываются к тексту пунктов классификатора, а не к кодам.** Группа
   «Смена дуги на верхней челюсти» обрабатывается правилом дуги, где бы она ни
   стояла и как бы ни была пронумерована. Известные правила (уже есть в v4):
   жалобы (раздел, начинающийся с «Жалобы» — выбирается один вариант, по умолчанию
   «не предъявляет»), тип системы, этап, слизистая, гигиена, соотношение моляров/клыков
   справа/слева с классом, состояние брекет-системы, смена дуги верх/низ (размер,
   материал, раскладка — см. тесты), смена лигатур, подвязывание, эластики,
   юстировка, контроль (сироты 4h1/4h2 — по типу системы), динамика, явка через N недель.
   **Новые варианты в известных группах работают без правки кода**, если их название
   врач пишет в записи (решение заказчика): новая резинка («Слон»), новый срок явки
   («3 недели»), новая жалоба, этап — правило ищет в записи слова/числа из текста
   вариантов в файле, а не из списка в коде. Не покрывается в 0.1 beta: новый материал
   дуги и синонимы («бета» = TMA) — это словарь сокращений следующей версии; до тех
   пор — предупреждение.
2. **Группа без известного правила** (врач добавил новую): вариант выбирается по
   словам из записи; не нашлось — группа в протокол не попадает.
3. **Одиночный пункт раздела** (без вариантов) попадает в протокол всегда. Это
   заменяет ручной список `fixed_ids` из конфига.
4. **Раздел** выводится заголовком, если в нём есть хотя бы одна строка.
5. **Как выводится группа с выбранным вариантом** — по эталонам: если в F строка
   группы содержит текст родителя + текст варианта (сейчас `2b`, `2c`) — склеиваем
   в одну строку; если родитель и вариант идут отдельными строками (`3k`, `4b`, `5d`)
   — отдельными строками; если родитель заканчивается на «:» (`3e`, `3g`) — только
   вариант. Для групп, которых нет в эталонах: «:» → только вариант, иначе
   отдельными строками.
6. **Разбор записи врача** — как в v4: нормализация смешанной раскладки, разбор
   дуг по челюстям, классы, недели и т.д. Все 35 тестов `test_ortodont.py` и сверка с
   эталоном `order.xlsx` должны проходить.
7. **Предупреждения** (оранжевым в строке статуса, пишутся в журнал) — по
   конкретному списку проверок, а не «каждое непонятое слово» (*моё решение*):
   дуга упомянута, но размер не распознан; такой дуги нет в классификаторе;
   упомянута резинка/срок/жалоба, которой нет среди вариантов; правило не нашло
   в файле свою группу (врач переименовал её до неузнаваемости); упоминание
   клыков/моляров без распознанного класса — *не* предупреждение (эталон
   «класс по молярам 1 и клыкам» это требует).
8. **Значения по умолчанию** (не предъявляет; этап рабочий; слизистая, гигиена,
   брекет-система в норме; динамика по плану; явка 4 недели; лигатуры на обеих
   челюстях при лигатурной системе) остаются — их требует эталон. В строке статуса
   серым: «по умолчанию: этап рабочий, явка 4 нед…» — чтобы врач видел, что не
   было написано им (*моё решение*).

## Интерфейс

Технология — tkinter + тема в стиле Windows 11 (например, `sv-ttk`): маленький exe,
быстрый старт. *Решение исполнителя/моё, заказчик не возражал.*

Одно главное окно, адаптивное по ширине (макеты A и B согласованы в браузере):

- **Широкое окно**: слева «Краткая запись», справа «Протокол». **Узкое**: запись
  сверху, протокол снизу. Переключение автоматически при изменении ширины.
- **Шапка**: «Orthofill» + метка «0.1 beta».
- **Строка файла**: имя открытого xlsx и состояние («✓ 124 пункта · эталоны 1/1»
  или «⚠ эталоны 1/2 — подробнее»), кнопка «Открыть файл…».
- **Краткая запись**: поле ввода в фокусе при запуске. **Ctrl+Enter** —
  сформировать и скопировать. Рядом кнопка «Сформировать и копировать».
- **Протокол**: редактируемый текст; постоянная заметная плашка «Проверьте протокол
  перед вставкой в служебное ПО». Кнопки «Копировать» (копирует текущий, в т.ч.
  исправленный текст) и «Сохранить как эталон».
- **Строка статуса**: «Скопировано в буфер», предупреждения оранжевым.
- **Закрепить поверх окон** — переключатель (для узкого режима рядом со служебным ПО).
- **О программе**: версия, путь к файлу классификатора и к базе, фраза «Программа
  формирует черновик протокола; ответственность за содержание несёт врач».
- Размер/положение окна, режим «поверх окон», последний файл — запоминаются.

Стиль: спокойный, светлый, крупный читаемый шрифт (Segoe UI), один акцентный
цвет, минимум элементов.

## «Сохранить как эталон»

Дописывает в xlsx новый эталон: строку с C = следующий номер, D = запись врача,
и ниже строки E/F = коды и строки протокола в том виде, в каком врач его оставил.
Пишется после последней занятой строки в колонках C–F.

- Только по явному нажатию; перед записью — подтверждение.
- Перед записью — резервная копия рядом (`<имя>.bak.xlsx`, последняя).
- Если файл открыт в Excel и заблокирован — понятное сообщение «Закройте файл в
  Excel и повторите», ничего не теряется.
- Файл может содержать форматирование/формулы, которые теряются при записи через
  openpyxl — заказчик принял этот риск; резервная копия есть.
- Если врач правил текст протокола: строки, совпадающие со строками классификатора,
  получают их коды; изменённые/новые строки пишутся в F без кода (E пусто) — сверка
  покажет их как расхождение, это сигнал доработать правило.

## Журнал (SQLite)

`orthofill.db` рядом с exe (если папка недоступна для записи — в
`%LOCALAPPDATA%\Orthofill\`). Python `sqlite3`, без внешних зависимостей.

xlsx — источник правды; база — память программы. Классификатор в базе не правится
и не используется для работы.

Хранится:
- каждое формирование: время, запись врача, выданный протокол, предупреждения;
- каждое копирование: итоговый скопированный текст (с правками врача) — разница
  между выданным и скопированным — главный материал для улучшения правил;
- отметка «сохранено как эталон»;
- снимок классификатора: контрольная сумма файла, имя, время, содержимое — чтобы
  знать, какой версией файла сделан каждый протокол;
- настройки (последний файл, окно) — можно здесь же.

## Сборка exe

`build.ps1` в корне проекта, запускается на Windows-машине (тестовой) одной командой:

1. ставит `uv`, если его нет (официальный установщик astral.sh);
2. `uv` сам скачивает подходящий Python и зависимости (`openpyxl`, тема, `pyinstaller`);
3. прогоняет тесты; падение тестов — сборки нет;
4. PyInstaller `--windowed`, иконка, данные темы, два результата:
   - **основной — портативная версия** (решение заказчика):
     `dist\Orthofill-0.1beta-portable.zip` — папка `Orthofill\` с `Orthofill.exe`
     внутри (сборка в папку, не one-file). Распаковал куда угодно — работает, без
     установки; `orthofill.db` и настройки — рядом с exe;
   - дополнительно `dist\Orthofill-0.1beta.exe` (one-file) — если в клинике его не
     блокирует антивирус.

Python на машине заранее не нужен, нужен интернет на время сборки. Проверка
интерфейса, буфера обмена и темы — на тестовой Windows-машине заказчика.
